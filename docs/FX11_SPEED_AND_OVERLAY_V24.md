# v24 仪表车速与叠加黑底诊断

## 车速

用户在 2026-10-18 反馈原厂车速 1–10 km/h、自定义仪表为 0。v23 的三套仪表使用 Android 标准速度 `0x11600207`。停车采样标准速度与 OEM 指示速度均为 0，不能凭停车零值推断行驶校准已经验证。

AutoService 随包 `car_properties.json` 将属性 10001 标为整数 km/h；FX11 映射直接读 `557874773 / 0x21407e55 / SIVehSpdIndcd`，没有比例变换。实车目录未列出该属性，但直接读取返回 status=0、area=0、INT32=[0]。

- 新增独立 `INDICATED_SPEED_KPH`，三套自定义仪表统一使用此来源，原始整数按 km/h 显示。
- 仅这个固定属性允许缺失目录；已声明的访问权限和区域限制继续生效。
- 拒绝负值、非整数、超出 350 km/h、错误状态、空载荷、错误属性/区域和超过 2 秒的速度事件。失效显示“—”，不回退到可能固定为 0 的标准信号。
- 保留标准速度和 OEM 速度的独立诊断；普通 CarPlay/iAP2 的标准速度协议保持原样。
- 单元和渲染回归覆盖 0、1、3、10 km/h、状态失效、事件超时，以及三套仪表不受标准零值覆盖。真实行驶对照仍待用户日常使用反馈，不要求为验证专门行驶。

## 原厂叠加黑底

用户确认只有中央地图，原厂表盘未显示。当前模式只绘制手机地图、导航文字和音乐，透明部分预期由原厂仪表填充；没有合成成功时不能用假的原厂圆盘填补。

实车证据 `outputs/fx11-v24-speed-investigation/`：

- Android display 4 / local:131 为当前仪表输出，1920×532；display 3 / local:130 当时无窗口。
- 窗口 type=2037、format=TRANSLUCENT，未设置 DIM_BEHIND。SurfaceFlinger 对应层 `blend=PREMULTIPLIED`、`isOpaque=false`，只有 DiPlay 的一个图层。
- Android 整屏截图地图外为黑色，alpha=255。但截图可能在捕获时将透明区域合成到黑色上，不能单独证明我们的窗口缓冲区不透明，也看不到 QNX 原厂层。
- 当次读到模式 0；服务缓存记录用户已从 3 切回 0。此前地图出现不能证明 3 在这台固件上正确保留 OEM 层。
- AutoDisplay 的静态代码包含普通透明窗口和可选 HAB→QNX 独立通道；样例屏幕配置未给出 FX11 对应关系。不能据此猜测更换 displayId 或保证普通透明窗口已足够。

v24 增加一次性 PixelCopy 诊断，在实际窗口缓冲区外侧采样 alpha，不保存地图或音乐像素；同时记录真实 displayId/屏幕名称 和手机地图流、导航、歌曲标题是否存在。它可以区分应用窗口不透明与后续合成问题，但不能自行确认物理仪表叠加成功。0/3 写入仍只响应用户明确 MODE 操作；没有新增保活、自动切换或 QNX 部署。

当前选择 NAVIGATION 时音乐区域隐藏；导航文字仅在手机提供导航数据时显示。选择 ALL 才同时显示有数据的地图、导航和音乐。上述页面规则与原厂圆盘消失是两个不同问题。

完整构建、签名、运行资产保留和安装结果见输出目录的 verification.json / installation.json。原厂物理合成未通过前维持“实验性”，不得报告修复完成。
