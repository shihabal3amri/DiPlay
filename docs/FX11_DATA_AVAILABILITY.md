## 为什么不直接用示例软件里的“读取和订阅”

可以直接用它背后的车辆属性接口。示例软件是这个接口的查看工具，不是另一份独立数据源。
它允许按已知属性 ID 显式读取，即使配置目录里没有该 ID；DiPlay 原来要求目录先声明可读，
因此在实际读取前就跳过了油量、续航和胎压。问题主要在 DiPlay 的筛选规则与单位/数据源选择。

v10 在 DiPlay 内直接通过同一类 HIDL 车辆属性服务读取，不依赖示例软件运行，也不抓取其界面。
只给上述 **7 个已验证反馈属性**（油量 1、DTE 1、胎压 4、温度 1）设置
`Binding.allowMissingConfig=true`。这不代表任意属性都能可靠读取或解释：

- 仅在配置条目缺失时允许这些绑定尝试只读 `get()`。
- 如果目录明确声明不可读、仅写，或不支持 area 0，仍拒绝读取；不会改为写入或换区域试探。
- 返回结果必须 OK，prop/area 必须匹配，value status 必须为 0；payload、PA active、范围和
  时间戳校验继续生效。读取失败当场清空，超过 2.5 秒没有成功确认则过期。
- 不改变普通 CarPlay 的基础绑定和配置筛选；新增厂商温度只是原生仪表的独立信号。
- 原生数据源仍可读取标准续航和标准温度用于诊断，但它们在本车与原厂对照不符，不再作为
  原生仪表 `rangeKm` / `ambientC` 的回退显示来源。
- 显式读取成功不能证明未声明属性的订阅也可用。本次保留周期读取和过期处理，不把订阅无事件
  当作当前值一直有效。

三套仪表 Midnight、Panorama、Replica 继续使用同一数据快照；此次修正不更换布局、按键行为
或普通 CarPlay 连接逻辑。ACC 设定速度及车道居中的未确认状态继续显示未知。

## 验证与诊断解释

修复后的安装验证应确认诊断中上述 7 项不再因为缺配置直接跳过，检查实际收到的 PA 和温度，
并与同一时刻原厂显示对照。车辆可能已变化，不能强求新采样仍为 17、111、23、23.3。
断开、失败、不可用或过期时必须回到未知；原厂 DTE/温度无有效值时不使用标准值替代。
新版打包、安装和实车结果另行记录；这些修复前的采样不是新包验收结果。

| 诊断信息 | 含义 |
| --- | --- |
| `config missing` | 目录缺条目，不等于接口不支持；只有本次 7 项白名单可在缺配置时继续尝试读取 |
| `config not readable` / `global area 0 missing` | 明确权限/区域不符合，保持拒绝 |
| `result=...` / `value status=...` | HAL 返回结果或值有效性；失败值不供显示 |
| `PA availability != 1` | 包未处于 Active，data 不能作为实时值 |
| `payload unavailable or unsupported` | 类型、长度或数值槽不符 |
| `decode rejected` | 超范围或未知枚举 |
| `timestamp rejected` | 零、未来或（仅速度）过旧源事件 |
| `lastAcceptedAgeMs > 2500` | 已不再作为当前车况显示 |

ON_CHANGE 的正旧时间戳本身不说明失效；成功 `get()` 会刷新接收时间，停止或失败仍过期。
v9 的数值槽兼容、逐属性诊断、只在连续三秒无进展时停止的 watchdog 继续保留。
本次成功采样没有证明需要放宽时间戳或状态检查。
